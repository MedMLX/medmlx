MedMLX native conversion

Use architecture recipes, a small shared operator layer, and independent source comparisons. Convert both the computation graph and its tensor state. Admit each new operation explicitly.

Capture, source translation and comparison recipes live in the conversion/ subproject (the medmlx_convert package). The portable graph schema, loader, Metal executor and shared geometry live in medmlx-core. Current native inference imports neither Torch nor Core AI/Core ML. This is an experimental fixed-shape FP32 path; complete host pipelines and catalog-wide conversion remain outside this pilot.

Implemented path

Original upstream model + checkpoint → strict torch.export → functionalization with an empty decomposition table → versioned schema-2 portable graph + Safetensors → medmlx-core Metal execution

Capture, functionalization, and reloaded MLX output are each compared directly to the original model. The graph retains explicit tensor references, source names, roles, shapes and dtypes. Consumed persistent buffers, nonpersistent buffers and constants are stored alongside parameters. Unknown operators, training, input/state mutation and unsupported variants fail explicitly. File loading happens on the host; model arithmetic runs on Metal.

The graph ontology, Torch frontend, MLX lowering and comparison gate are separate modules. The runtime preserves source tensor axes between operations and adapts layouts locally. This is a correctness baseline, without a throughput claim.

FDG PET simulation and radiomics have no learned checkpoint to convert. Aggregator and MCP repositories provide integration, rather than another neural architecture. Official TensorFlow SynthMorph is an additional source pipeline, not an already completed MLX model package.

Next work, in order

  1. Expand the working 2D/3D operator path using the existing CNN recipes. Reuse medmlx-core; add variants only with independent numerical evidence.
  2. Port SynthMorph's remaining affine fitting, affine/dense composition and hyperconvolution runtime with official TensorFlow intermediate fixtures. Admit released weights only after matching their exact architecture.
  3. Add attention and token-layout contracts, then explicit state inputs/outputs for SAM memory, language caches and diffusion trajectories.
  4. Keep host preprocessing/postprocessing in model recipes and compare complete pipelines separately. Precision optimization and performance measurements come after the source FP32 baseline.

Do not build a universal Python transpiler. The observed torch2mlx failures involved semantics that layer names alone cannot express. An ONNX route can provide another comparison, but an execution provider's CPU fallback does not establish native Metal coverage. Compatible Keras code can use its Torch backend; TensorFlow-specific custom code still needs migration. These are bounded engineering choices, not claims that one route is universally best.

Ownership and installation

Model applications need only medmlx-core and their model package. Conversion tools and upstream frameworks stay in medmlx_convert. The canonical schema and codec are defined once in core; ATen names are translated before serialization. Schema-1 pilot bundles require regeneration. The core runtime never imports the converter.
